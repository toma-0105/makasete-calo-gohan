# まかせてカロごはん

![まかせてカロごはん](public/ogp.png)

**献立を考えなくても、ダイエットは続く。**

身長・体重などから1日の目標カロリーを算出し、アレルギーを避けた「朝・昼・夕の献立」を自動で提案するWebアプリです。

|  |  |
|---|---|
| 公開URL | https://makasete-calo-gohan.toma15.com |
| すぐ試す | トップページの「ゲストでログイン」を押すだけ。アカウント登録は不要です |

---

## サービスの背景

数ヶ月前、ダイエット中の友人がこう話していました。

> 「毎日、1日の摂取カロリー内で献立を考えるのが一番のストレス。いっそ1週間分を誰かに決めてほしい」

私自身もダイエットで挫折した経験があり、一番の壁は「何を食べれば正解か」を考え続ける負担でした。
続かない原因は意志の弱さではなく、毎日判断を求められる仕組みにあると考え、その判断を代わりに引き受けるアプリを作りました。

## 解決したい課題

| | |
|---|---|
| 表に見えている困りごと | 1日の消費カロリー内で献立を考えるのが負担で、毎日「何を食べればいいか」を考え続けるのがストレス |
| 本当に解決したい課題 | 「この食事で合っているのか」という不安と判断の負担をなくし、迷わず続けられる食生活をつくること |

## 想定ユーザー

- 自炊が中心の人
- 毎食の献立やカロリーを考える負担が積み重なり、食事管理が続かなくなってしまう人
- 食事記録アプリは使っているが、「何を食べるか」を決めるのは自分でやっている人

## 機能紹介

| 機能 | 説明 | ゲスト | 会員 |
|---|---|:---:|:---:|
| 認証 | メールアドレスまたはGoogleで登録・ログインでき、パスワードの再設定にも対応しています。登録なしで試せるゲストログインもあり、ゲストから会員になっても、入力済みのTDEEやアレルギーはそのまま引き継がれます | ○ | ○ |
| TDEE診断 | 身長・体重・年齢・性別・活動レベルから1日の消費カロリー（TDEE）を算出し、無理なく続けられる1日の目標カロリーを大きく表示します | ○ | ○ |
| アレルギー設定 | アレルゲンを選択式で登録します。該当する食材を使った料理は献立から除外されます | ○ | ○ |
| 献立の自動生成 | 目標カロリーに合わせて、朝・昼・夕の献立（1日分）を提案します。料理の分量まで調整して目標に近づけます | ○ | ○ |
| 1品ごとの入れ替え | 気に入らない1品だけを、別の料理に入れ替えます。入れ替え前に近いカロリーになるよう、分量も調整します | ○ | ○ |
| 献立の再生成 | 1日分の献立をまるごと作り直します | ○ | ○ |
| 日数を選んで生成 | 1〜7日分の献立をまとめて生成し、日ごとのアコーディオンで一覧表示します | × | ○ |
| お気に入り | 気に入った料理を登録すると、次回以降の生成で優先的に選ばれます | × | ○ |
| 体重記録とグラフ | 体重の推移をグラフで確認できます。記録すると新しい体重でTDEEと目標カロリーを自動で再計算します | × | ○ |
| TDEE再診断のリマインド | 最後に診断してから30日たつと、見直しを促します | × | ○ |

## 基本的な使い方の流れ

```
トップページ → ログイン → アレルギー設定 → TDEE診断 → 目標カロリーの表示 → 献立の生成
```

1. トップページのゲストでログイン又は新規登録します（Googleで新規登録できます）
2. 食物アレルギーがあれば選びます（任意。なければスキップできます）
3. 身長・体重・年齢・性別・活動レベルを入力して、TDEE診断をします
4. 1日の目標カロリーが表示されます
5. 「献立を生成する」を押すと、朝・昼・夕の献立が表示されます。気に入らない料理は入れ替えられます

---

## 技術的に工夫した点

### 献立生成のしくみ

1. TDEEから目標カロリー（TDEE×0.85）を算出します
2. アレルゲンを含む料理を除外します（料理ごとの材料とアレルゲンを紐付けて判定）
3. 目標カロリーを朝25%・昼35%・夕40%に配分し、主食・主菜・副菜（または一品料理）を組み合わせ、汁物を加えることもあります
4. 料理ごとの`scaling_type`（調整不可／グラム単位で調整可／個数単位で調整可）に従い、分量の倍率で目標に近づけます。主食の増量には上限を設け、不足分は主菜で補うことで、炭水化物に偏らないようにしています
5. 合計カロリーが目標の90〜100%に収まるまで最大10回試行します。収まらない場合は、最も目標に近い案を採用します
6. 複数日を生成するときは、前の日に使った料理を除外し、同じ料理が続かないようにします

### 設計・品質面での工夫

- 責務の分離：ビジネスロジックは`app/services/`に切り出し、コントローラーはリクエスト・レスポンスの受け渡し、モデルはバリデーションとアソシエーションに絞っています
- 定数管理：配分比率・倍率・上限回数などの数値は、意味の分かる名前の定数で管理しています
- N+1クエリ対策：`includes`で事前読み込みし、Bulletをテスト環境で有効にしています（N+1が起きるとテストが失敗します）
- 権限の二重化：会員限定の機能は、画面でボタンを非表示にするだけでなく、URLを直接入力されてもサーバー側で拒否します

## サービスの差別化ポイント

| サービス | できること | 本サービスとの違い |
|---|---|---|
| [あすけん](https://www.asken.jp/) | 食事の記録、栄養分析、AIアドバイス | 記録と可視化に優れていますが、献立を自動で生成する機能はありません |
| [me:new](https://menew.jp/) | 最長1週間分の献立作成、苦手食材・アレルギーの除外、買い物リスト | 献立は作れますが、ユーザーごとの消費カロリーの範囲に合わせて生成する機能はありません。カロリーの調整はユーザーが行う必要があります |

既存のサービスは、情報の提供や記録には優れている一方で、「次に何を食べるか」を決める負担はユーザーに残っています。
本サービスは、記録ではなく意思決定の代行に絞っています。

1. 目標カロリーに収まる献立を、分量まで調整して提案する：TDEEから算出した目標カロリーに合わせて、料理の組み合わせと分量を自動で決めます
2. アレルギーを避けた献立を、登録なしですぐ試せる：ゲストログインで、アレルギー設定から献立の確認までを最短で体験できます
3. 「決められなかった」に応える：1品ごとの入れ替え、お気に入りの優先、日数の指定で、提案を自分に合わせて調整できます

## 技術スタック

### バックエンド

| 技術 | 選定理由 |
|---|---|
| Ruby 3.4.3 / Ruby on Rails 8.1 | 認証・DB・ルーティング・ジョブ管理まで標準機能が揃っており、「TDEE入力→献立生成→表示」の流れをMVCで一貫して実装できるため。規約に沿って書けば少ないコードで機能を追加できるので開発スピードが速く、MVPのリリース後も、フィードバックを受けて素早く改善を重ねられるため |
| PostgreSQL | Railsとの相性が良く、アレルギー除外やカロリー範囲での絞り込みなど、条件を組み合わせたクエリを扱いやすいため |
| Devise / OmniAuth（Google） | 認証の定番で、メール登録・パスワード再設定・Googleログインを安全に実装できるため。ゲストログインはService（`GuestUserCreateService`）で自作しています |
| ActiveJob / good_job | メール送信を非同期にするため。ジョブをPostgreSQLに保存でき、Redisなどの追加インフラが不要なため |
| Resend | パスワード再設定メールを、独自ドメインから安定して送信するため |
| rails-i18n / devise-i18n | 画面やエラーメッセージを日本語化するため |
| Sentry | 本番環境のエラーを検知するため |

### フロントエンド

| 技術 | 選定理由 |
|---|---|
| Tailwind CSS 4 / daisyUI 5 | ユーティリティクラスでレスポンシブなUIを素早く組め、ボタン・カード・モーダルはdaisyUIで統一感を保てるため |
| Hotwire（Turbo / Stimulus） | JSフレームワークを使わずに、ページ遷移や画面の動きをRailsのサーバーサイドと自然に連携できるため |
| esbuild（jsbundling / cssbundling） | JavaScriptとCSSのビルドを軽量にするため |
| Chartkick / Chart.js / groupdate | 体重の推移グラフを、少ないコードで描画するため |

### インフラ・開発環境

| 技術 | 選定理由 |
|---|---|
| Render | Railsアプリをデプロイしやすく、コストを抑えて運用できるため。ヘルスチェック（`/up`）で死活監視しています |
| Neon | マネージドなPostgreSQLで、過去の時点へ戻すInstant restoreが使えるため。復元の手順書を用意しています |
| 独自ドメイン | `onrender.com`へのアクセスは独自ドメインへ301リダイレクトし、URLを一本化するため |
| Cloudflare | 独自ドメインの取得と、DNSの管理に使うため |
| Docker | 開発環境を統一し、環境差異によるトラブルを防ぐため |
| Google Analytics | 本番環境でのユーザー行動を把握し、改善に活かすため |

いただいたフィードバックから、次のような機能を検討しています。

- 食事スタイルに合わせた生成（例：朝は食べない人は、昼と夜で目標カロリーを配分する）
